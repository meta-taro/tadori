# tadori の使い方

tadori は、仕様の 1 文から試験ケース・実施の記録・指摘・再発防止までを ID でつなぐ、git 上の台帳です。
工程ごとのルールで「どこが漏れているか」を出します。**漏れを認めるのは人です。**
言葉の意味は道具 `glossary` で引けます（漏れ・完了判定・残課題・タスクなど）。

## start はじめ方

1. 案件のフォルダを 1 つ決めます。設計書や試験シートのある案件のリポジトリの中でも、外の別のフォルダでもかまいません。
   外の人に見せられない案件は、案件のリポジトリの外に置き、push 先の無い git にします。
2. tadori の設定と台帳を置きます。どちらか一方で：
   - デスクトップアプリ：「ファイル › 新しく始める…」でフォルダを選び、「始める」を押す
   - コマンド：`tadori init <フォルダ> --name <案件の名前>`
   すでにあるファイルは書き換えません。commit もしません。
3. 置かれるもの：
   - `.tadori/phases.tsv` 工程（叩き台は 設計・実装・試験・リリース。会社や案件に合わせて書き換える）
   - `.tadori/statuses.tsv` WBS のタスクのステータス
   - `.tadori/rulesets/*.tsv` 工程ごとのルール（最初は例がコメントで入っているだけ）
   - `ledger/items.tsv` 台帳（設計書の章・試験ケース・指摘などの行と、そのつながり）
   - `ledger/wbs.tsv` WBS のタスク
   - `ledger/approvals.tsv` 人の承認の記録
4. エージェントから使うなら、MCP に tadori を登録します：
   `claude mcp add tadori -- node <tadori>/packages/cli/dist/main.js mcp <案件のフォルダ>`
   **登録したあとは、Claude Code を立ち上げ直してください。**すでに動いているセッションには道具が出てきません（`/mcp` にも出ません）。
   MCP がまだ使えない間は、同じ使い方を `tadori how-to [話題]` でも読めます。
5. 工程 → WBS → 台帳 → ルールの順に書き（topic: ledger・rules）、`tadori check` で漏れを見ます（topic: check）。
   ルールが 1 つも無い工程は「ルールなし（まだ判定していません）」と出ます。通ったという意味ではありません。

## ledger 台帳の書き方

TSV（タブ区切り）です。`#` で始まる行はコメントとして読み飛ばします。値が無いセルは空のままにします（`—` や `N/A` で埋めない）。

`ledger/items.tsv` の列：
- `id` 行の ID。会議で口に出して言える短いものにする（例：DD-2.3・TC-07・F-02）。重複は止まります
- `kind` 行の種類（例：BD=基本設計の章、DD=詳細設計の節、TC=試験ケース、RUN=実施の記録、F=指摘）。読み方は `.tadori/kinds.tsv` に書けます
- `title` 名前
- `source` 原本の場所（例：`docs/detail-design.md §2.3`・`qa/test-spec.tsv`）。**中身は写さず、場所だけを書く**（正本を 2 つにしない）
- `refs` この行が元にしている行の ID。`、` か `,` で区切って複数書けます
- ほかの列はルールの `field`（filled）や `only` で使えます（例：`change` に 変わる／変わらない）。読み方は `.tadori/columns.tsv`

予定の表は `ledger/wbs.tsv` です。画面での呼び名を変えるには（例：スケジュール・工程表）、`.tadori/project.tsv` に `schedule_label` を書きます。予定の表が無い案件では、プロダクトの画面に工程ごとのルール・台帳の行・漏れ・承認待ちが出ます。

`ledger/wbs.tsv` の列：`id`（W で始める）・`phase`（工程の ID）・`name`・`start`・`end`（YYYY-MM-DD）・`status`（`.tadori/statuses.tsv` の ID。名前で書いてもよい）。

`.tadori/statuses.tsv` は行の順番に意味があります。1 行目は「まだ始めていない」、tone が `ok` の状態は「終わった」です。ほかの状態は「始まっていて、終わっていない」として数えます（遅れの日数が出ることがあります）。表に無い状態も同じに数えるので、`tadori check` とプロダクトの画面が一覧で知らせます。
書いても書かなくてもよい列：`owner`（担当）・`issue`（この作業の課題の ID）。人単位の 1 日の進行に使います（topic: daily）。
WBS のタスクは台帳の行（種類 `W`）としても辿れます。台帳へ書き写さないでください。

**md-business の検証シートは、そのまま読みます。**`.tadori/sheets.tsv`（列 `path kind id title refs`）に書くと、シートの各行が書き写さずに台帳の行になります。
- `path` 案件のフォルダの中のシート（1 行目が `#! md-business:test-spec-tsv/v1` のもの）
- `kind` その行の台帳の種類（例：`TC`）
- `id` `title` `refs` 行の ID・名前・元にしている ID に使う、シートの列名（例：`ケースID`・`項目`・`仕様`）。ID が空の行は md-business の行 ID（`r` ＋ 16 進 12 桁）で指します
- ほかの列は、台帳の列と同じようにルールで使えます。md-business で控えにした行は読みません
- tadori はシートに書きません。`item_update`・`item_remove` はこの行を断ります。md-business で直してください

`ledger/approvals.tsv` の列：`rule`（approval のルールの ID）・`status`（`承認` か、差し戻しなど）・`who`・`when`。
**ここは承認した人が書きます。エージェントは書きません。**

つながりは台帳に書かれた ID だけで決まります。推測でつなぎません。

## rules ルールの書き方

`.tadori/rulesets/` の中の TSV（工程ごとに分けてよい）。列は `id phase kind from to field only values group owner label`（`values`・`group` は使うルールが無ければ無くてよい）。

`kind` は判定 5 種類と `note`：
- `covered` from の種類のどの行にも、それを元にした to の種類の行がある（例：観点 V ごとに試験ケース TC がある）
- `refers` from の種類のどの行も、to の種類の行を元にしている（例：どの基本設計の章 BD にも WBS のタスク W が紐づいている）
- `filled` from の種類のどの行にも、field の列の値が入っている（例：詳細設計の節 DD に change が書いてある）
- `allowed` from の種類のどの行も、field の列の値が `values`（`a|b`）のどれか（例：試験の記録 RUN の結果が `OK|NG`）。空の行は `filled` で見る
- `approval` 人の承認が要る。tadori は `ledger/approvals.tsv` を見るだけで、代わりに承認しない
  - `from` に種類（例 `BD`）を書くと、その種類の行の `source` のファイルも見る。承認のあとにそのどれかが commit されたら承認待ちに戻し、どのファイルのどの commit が変わったかを出す。承認した人が変更を見て、`when` を見た日に書き直す。`when` が日付だけなら、同じ日の commit は承認の前とみなす。時刻で比べたいときは時刻まで書く（例 `2026-10-20T15:00+09:00`）
- `note` **判定しない、読むための約束**（朝会のカンペの書き方・チャットの返事の書き方・人とエージェントの間の約束など）。`label` に書く。漏れにならず、工程の「ルールあり」にも数えない。`phase` は空でよい（空にしてよいのは `note` だけ）

ほかの列：
- `only` 対象の行を `列名=値` で絞る（例：`change=変わる` の節だけ commit を求める）。`列名=a|b` はどれかに合う行、`列名!=値`（`列名!=a|b` も可）はそれ以外の行
- `group` ルールの分類。分類の名前と数は、案件ごとに `.tadori/rule-groups.tsv`（列 `id name order color scope`）で決める。画面と `list_rules` は分類ごとに見せる
  - `color` 画面の帯の色：none・wait・hole・ok・blue・green・yellow・red・purple・gray（空なら既定）
  - `scope` だれまでに効くか：`team`（チームで共有。git に入る）か `local`（その人とエージェントの間だけ）。`local` の分類に足したルールは `.tadori/rulesets/rules.local.tsv` に置き、git に入れない（`.tadori/rulesets/.gitignore`）。commit もしない
- `owner` 漏れを直す担当（例：設計担当・検証担当）。画面と `list_leaks` に出ます
- `label` 人が読む一文（例：観点ごとに試験ケースがある）
- `at` このルールをチェック項目としてエージェントに突きつける節目。`|` で分ける（例：`cases-written|before-judge`）。`checkpoint` を参照
- `check` その節目で突きつける項目の文（実物を見て答えられる問い）。空なら `label` を使う

例：
```
id	phase	kind	from	to	field	only	owner	label
R8	it	covered	V	TC			検証担当	観点ごとに試験ケースがある
R4	dd	filled	DD		change		設計担当	詳細設計の節に改修後の対応が書いてある
R2	bd	approval					レビュー担当	基本設計書をレビュー担当が承認した
```
台帳に無い ID を refs に書くと、組み込みのルール `ID` が漏れとして出します。

エージェントは `list_rules` でルールを読みます（`group`・`kind` で絞れる）。書く前に `note` の約束を読んで、それに従ってください。

## check 確かめ方

- `tadori check <フォルダ>` 工程ごとの漏れと承認待ち。漏れがあれば終了コード 1（CI でも使える）
- `tadori check <フォルダ> --log --who <名前> --why <理由>` 結果をチェックの記録（`.tadori/checks.tsv`・5W1H）に足し、案件が git リポジトリなら commit します。push は人
- `tadori why <ID> <フォルダ>` 1 行から上下に辿り、線が切れている所を出す
- MCP の道具：`get_remaining`（残課題）・`list_leaks`（漏れと担当と直し方）・`trace`（辿る）・`find_items`（行を探す）・`list_rules`（ルールと書くときの約束）

漏れごとに「担当」と「直し方（どのファイルの何行目の、どの列に何を書けば消えるか）」が出ます。
直したら、もう一度 check して、漏れが消えたことを確かめてください。

## checkpoint 節目で確かめる

書くときの約束は、効いてほしい時機に読まれないと効きません。節目では、そこに効くルールだけをチェック項目としてエージェントに突きつけ、全部を確かめた記録を残します。

- 節目：`cases-written`（試験ケースを書き終えた）・`before-judge`（判定を付ける前）・`before-post`（外へ投稿する前）・`before-commit`（コミット前）。案件が `.tadori/checkpoints.tsv`（列 `id name`）で決め直せる
- ルールを節目に効かせるには、ルールの `at` 列に節目を書き、`check` 列に項目の文を書く
- 節目では `checkpoint`（MCP。`at` と `target`）か `tadori checkpoint <フォルダ> --at <節目>` で項目を読む
- 1 つずつ実物を見て確かめ、`checkpoint_record` で記録する。項目ごとに結果（`ok` 確かめた／`na` 該当なし／`fixed` ミスを見つけて直した／`open` ミスを見つけたが未対応）と、確かめた場所（ファイル:行か台帳の ID）を書く。`fixed` と `open` には、何が抜けていて何をしたかを `note` に書く。1 つでも欠けていれば何も書かない
- 対象は WBS のタスク ID か台帳の ID。`before-commit` では stage してある変更が対象。stage してから記録し、そのあと stage の中身を替えない
- 記録は `.tadori/checkpoint-log.tsv` に足す（追記だけで commit する）。記録ごとに、その時点のルールセットの版（ルールのファイルの最後の commit）が残る。後で不具合が見つかったとき「ルールが無かった」のか「ルールを当てていなかった」のかを切り分けられる
- `tadori checkpoint verify <フォルダ> --at <節目> [--target ID]` は、最後の記録が、いま効くルール（あとから足したものも含む）を全部当てていないか、`open` のミスが残っていれば終了コード 1。git の pre-commit（`--at before-commit`）や、エージェントのフック（投稿の前）から呼ぶ。フックを入れるのは、その設定を持つ人

これはエージェント自身の記録で、人の承認ではありません。漏れを埋めたとは判定しません。

## daily 人単位の 1 日の進行

プロダクト単位の残課題とは別に、**人単位**で「1 日の進行」を出します（今日したこと・次の作業日にすること・相談）。

- 画面：左の「1 日の進行」（担当と日付を選ぶ。本文はその場で直せる。「下書きを作る」「足す」「消す」「文をコピー」）
- コマンド：`tadori daily <フォルダ> --who <担当> --date <YYYY-MM-DD>`（読むだけ）
- MCP：`daily`（読む・行の [ID] も出る）・`daily_generate`（下書きを作って置く）・`daily_add`・`daily_update`・`daily_remove`
- その作業でさわった正本の場所は、`daily_add`・`daily_update` の `links`（`[{ "label": "QA表", "url": "https://…" }]`・http と https だけ・8 件まで）で付けます。画面では行の末尾に「QA表 ↗」と出て押すと開き、読み上げる文には入らず、補足に「QA表：URL」で出ます。直すときは全件を渡し直します
- 行の小さな札は、`daily_add`・`daily_update` の `badges`（`[{ "text": "遅延", "tone": "hole" }]`・8 件まで・tone は none・wait・hole・ok）で付けます。**中身はエージェントか人が決めます**（遅延・確認待ち・期限 11/12 など）。tadori は値を判定せず、WBS の無い案件でも使えます。画面では本文とは別に tone の色で出し、文では行のうしろに出ます。直すときは全件を渡し直します（空の配列で消えます）
- 本文の語そのものをリンクにするときは、links の要素に `anchor`（本文の中の語）と、同じ語が何回も出るなら `nth`（何回目か）を足します。画面の「文の形」ではその語がリンクになり、行末には出ません。本文に見つからないときは行末に「表示名 ↗」で出し、道具の返事で知らせます。補足には今どおり「表示名：URL」で出ます
- 台帳の source の場所に URL をそのまま書いた行（例：`課題管理 https://…`）は、sources.tsv の locator を通さず、その URL を正本のリンクにします
- `issue` を渡した行は、足した行・直した行でも、自動の行と同じく頭に「課題番号 短い件名」が付きます

**下書きの材料**は、案件のリポジトリの中の記録だけです（外の道具とは同期しない）。
- WBS の状態の変化
- 台帳の差分（その日に足した行・直した行）
- その日のチェックの記録（`.tadori/checks.tsv`）

台帳の行を足した・直したことは、ふつうは**台帳の整備**として、今日の作業とは別の見出しに出します（成果物を直し終えたと読み違えないように）。
対応の記録や試験の記録のように、行を足すこと自体が「やったこと」に当たる種類は、`.tadori/kinds.tsv` に `work` 列を足して印（`yes`）を付けると、今日の作業として出ます。
台帳の差分は、commit の作者名を担当にします。WBS の担当と git の名前がそろっていなければ、`.tadori/members.tsv`（列 `name`〈担当〉・`git`〈git の作者名〉）に対応を書きます。

**課題ごとの要約（読み上げ用）。**1 つの課題で今日の行が多いときは、`daily_add` で要約を 1 つ足します（`section: summary`・`issue` が要る・1 日 1 課題に 1 つ）。要約の文は tadori が作らず、エージェントか人が書きます。型は「何があって → 今どの工程か → 今日終わるか → 終わったら何をするか」（確かめたいことがあれば最後に質問の形で）。例：「仕様変更があって、いまは結合試験の途中です。今日は終わりません。終わったらリリースの準備をします。」
画面の**読み上げ**では、要約のある課題は今日の欄の先頭に要約だけを出し、細かい行は出しません。**詳しく**は今までどおりです。`daily` に `read: true` を渡すと、読み上げの文が返ります。要約の無い課題は、どちらでも今の行のまま出ます。

**置き場所**は日ごとのファイル `.tadori/daily/YYYY-MM-DD.tsv` です（保存のたびに commit。push は人）。
人かエージェントが直した行・足した行・消した行は、下書きを作り直しても上書きしません。触っていない自動の行だけが、新しい材料で作り直されます。

前の作業日（それより前で、1 日の進行のファイルがいちばん新しい日）の「次の作業日」に人が足した行・直した行は、その日の「今日」にも予定として出ます。前の日の行はそのまま残ります。新しい日では自動の行と同じ扱いで、直す・消すとそれが残ります。

WBS（`ledger/wbs.tsv`）と台帳に、書かなくてもよい列があります。
- WBS の `owner`：担当。2 人以上なら区切って書く（・、, / のどれでも。どちらの名前でも絞れる）
- WBS の `issue`：この作業の課題の ID（台帳の行）。同じ課題の作業を 1 件にまとめる。推測ではまとめない
- 台帳の課題の行の `short`：短い名前。本文は `short` を使い、正式な名前（title）は補足に出す

状態が変わった日は、WBS の git の履歴（commit ごとの中身）から読みます。まだ commit していない書き換えは今日の変化として数えます。
**tadori を入れる前（WBS を git に入れる前）の変化は出ません。**入れた直後に「今日 0 件」になるのはそのためです。状態を変えたら、その日のうちに commit してください。

**文の形は案件ごとに決められます。**`.tadori/daily-format.tsv`（列 `key`・`value`）に、変えたいものだけを書きます。書かなければ既定の形です。

| key | 既定 | 意味 |
|---|---|---|
| `today` | `今日（{date}）{count} 件` | 今日の見出し（{date}＝M/D 曜、{count}＝件数） |
| `next` | `次の作業日（{date}）` | 次の作業日の見出し |
| `consult` | `相談` | 相談の見出し |
| `notes` | `補足` | 補足の見出し |
| `wbs` | `{id}` | WBS の番号の書き方（{id}＝ID そのまま、{num}＝先頭の W と区切りを外したもの） |
| `continued` | （空） | 次の作業日も続く作業の頭に付ける印（区切りが無ければ空白を 1 つ入れる） |
| `numbering` | `continuous` | 番号の振り方。`continuous`＝見出しをまたいで通し、`per-section`＝見出しごとに 1 から（補足は見出しの名前で分ける） |
| `today_label`・`next_label`・`consult_label` | `今日`・`次の作業日`・`相談` | `per-section` のとき、補足を分ける名前 |
| `upkeep` | `台帳の整備` | 台帳の行を足した・直したことの見出し（相談のあと・補足の前。今日の作業とは分ける） |
| `upkeep_mode` | `show` | 台帳の整備を出すか（`show`・`hide`） |
| `tag_done`・`tag_doing`・`tag_plan`・`tag_upkeep`・`tag_checked` | `済`・`作業中`・`予定`・`整備`・`確認` | 行の頭に付ける印の言葉（空にするとその印は出さない）。印は行のもとで決まる：今日に済みへ変わった＝done、途中の状態へ変わった＝doing、次の作業日＝plan、台帳の整備＝upkeep、チェックの記録＝checked。人とエージェントは行ごとに直せる |
| `tag_format` | `［{tag}］` | 印の書き方 |
| `who_format` | `{who}：` | 担当で絞っていない（全員の）文で、行の頭に付ける担当名の書き方。空なら付けない |
| `badge_format` | `〈{badge}〉` | 行のバッジを本文のうしろに出す書き方（バッジの数だけ並べる）。空なら文には出さない（画面には出る） |
| `stale_hours` | `3` | 待ちの行を、最後に直してから何時間で「古い待ち」として印を付けるか。0 なら付けない。待ちと読むのは、tone が wait のバッジのある行と、`wait_words` の語を本文に含む行だけ |
| `wait_words` | （空） | 本文にあれば待ちと読む語（例 `確認中・回答待ち・待ち`）。空ならバッジだけを見る |
| `intro` | （空） | 画面「1 日の進行」の頭に出す説明（空なら tadori の既定の説明） |
| `group_after` | `3` | 台帳の同じ種類の行をこの数より多く足した・直した日は、種類ごとに「○○を N 行足した」の 1 件にまとめる（ID は補足へ） |

作業をまとめて 1 件にするのは、同じ課題・同じ担当・同じ続き方（続く作業か、始まる作業か）が並んだときだけです。担当で絞ったときに、ほかの人の作業が混ざりません。

変わらないのは骨組みだけです：見出しは 今日 → 次の作業日 → 相談 → 補足 の順、番号は通しで、本文に場所を挟まず、正式な名前と場所は同じ番号で補足に出します。
**これは下書きです。**本文を中身の分かる言い回しに直す・並べ替える・相談を書くのは、人かエージェントです。

## write 書く道具（MCP）

台帳や設定の TSV を直に直さず、次の道具で書いてください。どれも形と ID を確かめてから書き、書いたあとに案件を読み直して、読めなくなる書き方は元に戻して断ります。書けたら commit します（push は人）。

- 台帳：`item_add`・`item_update`・`item_remove`（refs は台帳にある ID だけ。ほかの行が指している行は消さない）
- 正本から反映した記録：正本を見て手元の行を直したら `item_update` に `synced_by`（反映した人）を付ける。中身は変えずに「いまの正本どおり」と確かめただけなら `item_synced`（`id`・`who`）。日時は道具が入れる（`synced_at`・`synced_by` 列）
- WBS：`task_add`・`task_update`（状態・日付・担当・課題。その場で commit するので、1 日の進行の「状態が変わった日」がずれない）
- ルール：`rule_add`・`rule_update`・`rule_remove`
- 人の表：`member_set`・`member_remove`（人の役割 roles と git の作者名）
- 工程：`phase_set`（使われている工程は消せない）
- 確かめる：`run_check`（`log` を付けるとチェックの記録に 5W1H で足す）
- 案件：`list_projects`・`open_project`（この MCP の口で扱う案件を替える）
- 画面の裏の server の例外：`server_errors`（画面に「サーバーの中で問題が起きました」と出たとき、どこで何が落ちたかを新しい順に読む。記録は PC の手元にあり、案件のフォルダには置かない）
- いま話している MCP の版：`version`（版・組んだ commit と日時・`pnpm build` して /mcp でつなぎ直す必要があるか）。直したはずのものが出ないときに見る。席が始めのあとに足された道具を見られないときのために、話題なしの `how_to` の 1 行目と、MCP がつなぐときに名乗る版にも、版と組んだ commit（例 `0.0.1+7a08b11`）を出す
- 画面の担当の絞り込み：`screen` の `filter`

**人の承認を書く道具はありません。**承認（`ledger/approvals.tsv`）は、承認した人が書きます。

## screen 画面を見せながら案内する

人の画面（tadori のデスクトップアプリかブラウザ）を、**画面の中の専用カーソル**で操作して見せられます。人のマウスは使いません（奪いません）。
道具 `screen` に、次のどれかを渡します：
- `{ "action": "point", "target": "ルールセット", "message": "ここにルールがあります" }` 指して黄色の枠で示す
- `{ "action": "click", "target": "ルールセット" }` 押す
- `{ "action": "type", "target": "探す", "value": "DD-2.3" }` 欄に打つ
- `{ "action": "go", "hash": "#trace-F-02" }` 画面を移る（`#phases` `#rules` `#log` `#trace-<ID>` `#browse` `#settings` `#glossary`）
- `{ "action": "say", "message": "ここが漏れです" }` 一言だけ出す
- `{ "action": "filter", "value": "設計担当" }` どの画面も、その人（または役割）の分だけに絞る。`value` を空にすると全員に戻す

`target` は画面に出ている文字・ボタンの名前で探します（ぴったり同じ名前を先に）。
押せるのは人が画面で押せるものだけです。Windows のダイアログ（フォルダ選びなど）は操作できないので、人に頼んでください。
デスクトップアプリは `http://127.0.0.1:4873`、別の番号で開いているときは MCP を `--screen http://127.0.0.1:<番号>` で起こします。

## links ほかの道具を開く

`.tadori/links.tsv`（列 `tool url`）に URL の雛形を書くと、漏れの横の md / qa のアイコンが押せるようになります。
差し込める値：`{path}`（案件のフォルダからの場所）・`{repopath}`（git リポジトリの最上位からの場所）・`{abspath}`・`{line}`・`{id}`・`{rowid}`（検証シートの行の、md-business の行 ID）。差し込んだ値が空の引数は、リンクから外します。
例：`md-business	md-business://open?repo=github.com/<持ち主>/<リポジトリ>&path={repopath}&line={line}&id={rowid}`（md-business は `line=` より `id=` を使い、その行を選んだ状態でシートを開きます）
`javascript:` `data:` `file:` などの雛形は読み込みで止めます。

## sources 正本へのリンクと、反映した日時

台帳は手元の写しで、正本（文書・シート・課題）は外の道具にあります。`.tadori/sources.tsv`（列 `name url locator stale_days`）に正本を書くと、台帳の `source` 列の先頭がその名前の行に、正本へのリンクが付きます（画面のつながりのカード・1 日の進行・`find_items`・`trace`・`tadori why`）。
- `locator`：場所まで飛ぶ URL のひな形。`{url}`＝URL、`{loc}`＝名前のあとの文字、`{num}`＝その中の最初の数。空なら URL のまま
- `stale_days`：正本から手元へ反映してから、何日で「古い」と出すか（既定 14）。反映の記録（`synced_at`）が無い行も古いと出します
- 例：`課題表	https://issues.example.com/p	{url}/{num}	7` と書くと、`source` が `課題表 #12` の行は `https://issues.example.com/p/12` を開きます

tadori は正本と同期しません。古いと出た行は、人かエージェントが正本と見比べて、直したら `item_update`（`synced_by` 付き）、そのままでよければ `item_synced` で記録してください。
URL は案件の `.tadori/sources.tsv` にだけ書きます（tadori 本体には入れません）。

## agent-rules エージェントが守ること

- **漏れを埋めたと判定しない。** tadori が出すのは漏れの一覧まで。「確かにそこが漏れていた」「直った」と認めるのは人
- **承認しない。** `ledger/approvals.tsv` は承認した人が書く。MCP にも承認の口は無い
- **試験の結果欄を代わりに書かない。** 合否は実物を見た人が書く
- **割合や点数を作らない。** 伝えるのは漏れの中身と件数・承認待ち・ステータス・遅れた日数という事実だけ
- **台帳に原本の中身を写さない。** source には場所だけ。正本は原本の道具（md-business・git-qa など）にある
- **つながりを推測で足さない。** refs に書くのは、元にしたと分かっている行の ID だけ
- **commit まで。push は人が中身を確かめてから。**
- 人に画面を説明するときは `glossary` の言葉を使う（漏れ・完了判定・残課題・タスク・つながりを辿る）

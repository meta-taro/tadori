# ロードマップ — tadori

段ごとに「次へ進んでよい条件」を置きます。条件を満たさないまま次の段の機能を書き始めないこと。

## Phase 0 — 列の叩きと最小の判定（いま）

| # | 内容 |
|---|---|
| 001 | 架空の案件で SPEC / F / R の TSV を起こし、列の叩きを作る |
| 002 | `tadori check` の最小版 |
| 003 | `tadori why <ID>` の最小版 |
| 004 | md-business・git-qa へ「動かない ID」2 つを頼む（D4） |

**次へ進んでよい条件**: 架空の見本で `check` と `why` が動き、テストがある。

## Phase 1 — 実案件 2 件で回す（第 1 段・D5）

- 実案件の作業リポジトリの中で、既存の指摘を 2 案件分台帳に起こす（D3・このリポジトリには入れない）
- `check` が出した穴を人が読む
- 列の形が 2 件目で崩れたら、列を直して見本も直す

**次へ進んでよい条件（止めどころ）**: 人が「確かにそこが抜けていた」と言えた。
**言えなければ archive する。**

## Phase 2 — 改修の前に読む（第 2 段）

- `tadori before <改修>` を作る
- 次の改修 1 本で、着手前に `before` を読んでから入る
- md-business・git-qa へ PRD §7 の残り 5 項目を頼む（列の形が固まったので）

**次へ進んでよい条件**: その改修で、同じ原因区分の指摘が 0 件で終わった（PRD §9）。

## その後

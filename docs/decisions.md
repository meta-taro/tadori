# 決定と、その理由

tadori で決めたことと、なぜそう決めたかを残します。覆すときは理由を書いて新しい項を足します（古い項は消しません）。

## 2026-11-05 手元で開く画面を持つ

**`tadori serve` で、手元（127.0.0.1）に画面を開く。**

- 「リリースまで進めてよいか」は、工程をまたいだ完了判定・遅れ・記録を 1 か所で見ないと判断しにくい。CLI の一覧だけでは足りなかった
- ただし画面は判定を持たない。判定は CLI・CI と同じ核（`@tadori/core`）を通す。画面だけの判定を作ると、CI と結果が食い違う
- 割合（○%）や点数は出さない。出すのは漏れの中身と件数、人の承認待ち、タスクのステータス、遅れた日数という事実だけ。
  割合を出すと、それを上げるための形だけの行が増える

## 2026-11-05 正本は増やさない。tadori が書くのは設定と記録だけ

- 設計書・検証シート・WBS の正本は、それぞれの道具（md-business の文書・TSV）にある。tadori は読んでつなぐ
- WBS のタスクは台帳に書き写さず、読み込むときに台帳の行（種類 `W`）として扱う。書き写すと正本が 2 つになる
- tadori が書くのは、工程・ステータス・ルールセットの設定（`.tadori/`）と、チェックの記録（`.tadori/checks.tsv`・5W1H）。
  画面で WBS のステータスを変えたときは、`ledger/wbs.tsv` のそのセルだけを書き換える（ほかの行や `#` の行は触らない）

## 2026-11-05 保存は git の commit で残す。push は人

- 画面やエージェントが保存したら、案件のリポジトリに commit する。各担当が自分のクローンで作業して push すれば、全員の操作が履歴に残る
- push は人が中身を確かめてから行う。tadori は push しない
- 案件のフォルダがそれ自身の git リポジトリでないときは commit しない（ほかのリポジトリに記録が混ざるのを防ぐ）

## 2026-11-05 外の道具とは同期しない

- GitHub・GitLab・課題管理などは、エージェントがその都度読む
- 外の記録は後から書き換えられることがあり、止まれば読めなくなる。大事なのは「tadori がその時点でどう見たか」なので、
  読んだ時点の記録（時刻・取得元・要約・中身のハッシュ）を tadori の側に残す
- 認証は各道具の CLI や環境変数に任せ、トークンは設定にも台帳にも書かない

## 2026-11-05 手元の TSV の書き換えは、その場で画面に反映する

同期はしないが、**手元の案件のフォルダの TSV が書き換わったら、画面はその場で描き直す。**
md-business で原本を直し、git-qa で実施し、その結果を tadori の画面で同時に見る使い方のため。

- `tadori serve` が案件のフォルダを見張り、TSV が書き換わったら画面へ知らせる（Server-Sent Events・手元の中だけ）
- 保存は短い間に何度も起きるので、0.3 秒まとめてから知らせる。画面の欄に打っている途中なら、欄から離れたときに描き直す
- 外の道具（GitHub など）を見張るのではない。git pull で手元の TSV が入れ替われば、それも同じように拾う

## 2026-11-05 ほかの道具は URL の雛形で開く

md-business・git-qa からは URL スキームの形だけをもらい、tadori は URL を作って渡すだけにする。開いたあとの動きは先方の実装に任せる。
雛形は案件の `.tadori/links.tsv` に書く。押すと画面の中で命令が動く形（`javascript:` など）は読み込みで止める。
md-business はリポジトリと、その最上位からの場所でファイルを指すので、案件のフォルダがリポジトリの途中にあっても渡せるよう `{repopath}` を用意した。

## 2026-11-05 用語は「漏れ」

ルールが求めるつながりが無い箇所を「漏れ」と呼ぶ（以前の文書の「穴」）。人が最後に認める言葉も「確かにそこが漏れていた」にそろえる。

工程の出口（カードの終わり）で「この工程は終わったと言ってよいか」を確かめることを「完了判定」、
それを止めているもの（漏れと承認待ち）を「残課題」と呼ぶ（以前の文書の「関門」）。日本の開発の現場で通じやすい言葉にそろえるため。
WBS の 1 行は「タスク」と呼ぶ。言葉の一覧は packages/ui/static/glossary.tsv。

## 2026-11-05 ルールの判定は 4 種類

| 種類 | 意味 | 例 |
|---|---|---|
| `covered` | その種類のどの行にも、それを元にした下流の行がある | 観点ごとに試験ケースがある |
| `refers` | その種類のどの行も、上流の行を元にしている | どの基本設計の章にも WBS のタスクが紐づいている |
| `filled` | その種類のどの行にも、決めた列の値が入っている | 詳細設計の節に「改修後の対応」が書いてある |
| `approval` | 人の承認が要る。tadori は承認の記録を見るだけで、代わりに承認しない | 基本設計書をレビュー担当が承認した |

`only` 列（`列名=値`）で対象の行を絞れる（例：改修後に「変わる」節だけ commit を求める）。
つながりは台帳に書かれた ID だけで決める。推測でつながない。

## 2026-11-05 技術の選び方（MVP）

| 何に | 何を | なぜ |
|---|---|---|
| パッケージ管理 | pnpm（workspace） | install script の許可制と、公開直後の版を入れない設定が標準で使える |
| 判定の核・CLI | TypeScript・Node 22 以上。実行時の依存は持たない | 判定は CI でも pre-commit でも動く必要がある。依存が少ないほど壊れにくい |
| テスト | Vitest | TypeScript をそのまま走らせられ、速い |
| 画面 | ビルドの要らない素の JavaScript（ES modules）を `tadori serve` がそのまま配る | 叩きから早く移すため。**型が無いのは借り**で、次の段で TypeScript に移す |
| サーバー | Node の `http` だけ。127.0.0.1 にだけつなぐ | 同じ網のほかの PC から見えないようにする。書き込みには独自ヘッダを求め、ほかのサイトからの書き込みを防ぐ |

デスクトップアプリとして包む（Tauri など）・資料の版と差分の画面は、次の段で決める。

## 2026-11-06 デスクトップアプリは Tauri 2 で包む

**Tauri の窓が裏で `tadori serve` を起こし、その画面を窓に映す。**判定もサーバーも TypeScript のまま。

- 判定を Rust で書き直すと、CLI・CI・MCP と窓とで判定が 2 つになり、結果が食い違うおそれがある。窓は起こして映すだけにする
- 連携する md-business も Tauri で、Node を裏で起こす同じ形をとっている。道具と作法をそろえられる
- 窓が開くのは、自分で起こした 127.0.0.1 の画面だけ。画面から Rust 側の機能を呼ぶ口は作らない（フォルダ選びは Rust 側で済ませる）。サーバーの守り（Host・Origin・独自ヘッダの検査）はそのまま効く
- 採らなかった案：Electron（配る大きさが大きく、md-business と道具がそろわない）、判定の Rust への書き直し（上の理由）
- Node は PC に入っているものを使う。Node の無い PC に配る必要が出たら、Node を同梱する方式を別に考える

## 2026-11-05 MCP の口は依存なしで書く

`tadori mcp` は、標準入出力に 1 行 1 つの JSON-RPC を流す MCP の決まりを、Node だけで書いた。
道具が少ないうちは短く書け、判定の核と同じく依存を増やさずに済むため。道具が増えて手書きが重くなったら、公式の SDK に替えることを考える。
最初の道具は用語の参照（`glossary`）。画面の「用語」と同じ `packages/ui/static/glossary.tsv` を読み、言葉を 1 か所で管理する。

## 2026-11-06 画面の配色は明るいものを既定にする

会議で画面を共有する職場では、暗い画面はなじみにくい。**明るい配色を既定にし、暗い配色と「OS に合わせる」は設定で選ぶ。**

- 選んだ配色は、その PC のブラウザ（デスクトップアプリの窓）に覚える。人の好みなので、案件の設定（TSV）には書かない
- 色の意味はどちらでも同じ（漏れ＝琥珀、承認待ち＝青灰、済み＝緑）。明るい背景で読めるよう濃さだけ変える
- デスクトップアプリは毎回同じ番号（4873・ふさがっていれば空いている番号）で開く。ブラウザは番号ごとに好みを覚えるため

## 2026-11-06 デスクトップアプリの上の帯は自作にする（窓の操作の口を絞って開ける）

Windows 標準のタイトルバーを消し、tadori の上の帯をタイトルバーにする（帯をつかんで動かす・メニュー・最小化／最大化／閉じる）。
連携する md-business と見た目と操作をそろえるため。

このため「画面から Rust 側の機能を呼ぶ口は作らない」を、次のように改める。

- 開けるのは、窓の操作（動かす・最小化・最大化・閉じる）と、案件を開く 3 つの命令（フォルダを選ぶ・最近の案件の一覧・最近の案件を開く）だけ
- 開ける相手は、自分で起こした 127.0.0.1 の画面だけ。ファイルの読み書きなどは開けない
- 「最近の案件を開く」は、最近の案件の一覧にある場所しか受けない（画面から好きな場所を開かせない）
- 自作の命令は、許した画面からだけ呼べる形にする（既定で誰でも呼べる形にしない）

## 2026-11-06 エージェントは画面の中の専用カーソルで操作する（人のマウスを奪わない）

エージェントが画面を操作して見せるとき、OS のマウスは動かさない。人が同じ PC で作業していても、手元のマウスを取り上げないため。

- エージェントは手元の tadori サーバーへ指示を送る（`POST /api/agent`：指す・押す・打つ・移る・話す）。サーバーは開いている画面へ流す
- 画面は自分の専用カーソル（「エージェント」の札つき）をその場所へ動かし、黄色の枠と一言で示してから、ページの中で押す
- 押せるのは、人が画面で押せるものと同じものだけ。判定や保存の近道は作らない。指示の口は、書き込みと同じ守り（独自ヘッダ・Origin・Host の検査）を通す
- OS のダイアログ（フォルダ選びなど）は操作できない。そこは人が行う

## 2026-11-09 インストーラーは OS と CPU ごとに GitHub Actions で作る

macOS（Apple シリコン・Intel）と Windows（x64・ARM）のインストーラーを、人が `v` で始まるタグを push したときに作り、**下書きのリリース**に付ける。下書きを公開するのは人。

- アプリの中には、ビルド済みの tadori（CLI・判定の核・画面・使い方）をそのまま写して入れる（`packages/desktop/scripts/stage.mjs`）。判定の核は実行時の依存を持たないので、バンドラを足さずに済む
- Node.js は PC に入っているものを使う（22 以上）。同梱は、Node の無い PC に配る必要が出たときに考える
- コード署名はまだ無い。初めて開くときに OS が確認を求めることを、サイトのダウンロードのページに書いた

## 2026-11-09 紹介のサイトは、ビルドの要らない静的な HTML にする

`site/` を GitHub Pages に出す（トップ・事例・ダウンロード・過去の版・ロードマップ）。

- ビルドの道具を足さない。速く、検索エンジンや AI の検索の道具にもそのまま読める
- 画面のキャプチャは、架空の見本の案件だけで撮る。実案件や個人の情報は載せない
- 版の一覧とダウンロードのボタンは、見る人のブラウザが GitHub のリリースから読んで作る（サイトを版ごとに直さずに済む）
- 構造化データ（JSON-LD）・サイトマップ・`llms.txt` を置き、検索と AI の回答に、要点（漏れを認めるのは人・割合を出さない・手元で完結）が正しく伝わるようにする

## 2026-11-09 人単位の「1 日の進行」を出す

PM はプロダクト単位と人単位の両方で進行を見る。プロダクト単位の残課題に加えて、担当ごとの 1 日の進行（今日したこと・次の作業日にすること・相談）を出す（画面「1 日の進行」・`tadori daily`・MCP の `daily`）。

- 材料は案件のリポジトリの中の記録だけ（WBS の状態の変化・台帳の差分・チェックの記録）。外の道具とは、ここでも同期しない
- WBS に、書かなくてもよい列を 2 つ足す：`owner`（担当）と `issue`（この作業の課題の ID）。課題は `issue` に書かれたものだけで、推測でまとめない
- 状態が変わった日は、WBS に日付の列を足さず、WBS の git の履歴から読む。日付を手で書く列を作ると同じ情報が 2 か所になり、ずれるもとになるため
- 下書きは日ごとのファイル（`.tadori/daily/YYYY-MM-DD.tsv`）に置く。チェックの記録と同じく、tadori が書く記録として `.tadori/` に置き、保存のたびに commit する（push は人）
- 各担当は画面で直し、エージェントは MCP で足す・直す・消す。直した行・足した行・消した行は、作り直しても上書きしない
- **文の形（見出しの言葉・WBS の番号の書き方など）は本体に固定しない。**チームごとに違うので、案件の `.tadori/daily-format.tsv` で決める。本体の既定は、特定のやり方に寄らない一般的な形にする
- tadori が出すのは下書きまで。本文の言い回し・並べ方・相談は人かエージェントが書く。割合や点数は出さない

## 2026-11-09 MCP に書く道具を足す（承認の口は作らない）

エージェントが台帳や設定の TSV を直に直すと、形の崩れや、台帳に無い ID へのつながりが紛れ込む。書く道具を MCP に足し、道具を通して書く。

- 台帳の行・WBS の作業・ルール・人の表・工程を書く道具と、記録つきの check、案件の切り替え（`open_project`）
- どの道具も、書いたあとに案件を読み直し、読めなくなる書き方は元に戻して断る。refs は台帳にある ID だけ（推測でつながない）。ほかの行が指している行は消さない
- 書けたら commit する（push は人）
- **人の承認を書く道具は作らない。**承認は人だけが行う

## 2026-11-09 正本へのリンクと「正本から手元へ反映した日時」を出す

台帳は手元の写しで、正本は外の道具（文書・シート・課題の管理）にある。写しが古いまま読まれると、漏れの一覧そのものを信じられなくなる。

- `.tadori/sources.tsv` に正本の名前・URL・場所まで飛ぶひな形・「古い」とする日数を書く。台帳の `source` 列の先頭がその名前なら、画面・1 日の進行・MCP に正本へのリンクを出す。URL は案件の側にだけ置き、tadori 本体には持たない
- 台帳の行に `synced_at`・`synced_by`（正本から手元へ反映した日時・だれが）を書く。MCP の `item_update`（`synced_by` 付き）か `item_synced` で、日時は道具が入れる。設定の日数を超えた行・記録の無い行は「古い」と目立たせる
- tadori は正本と同期しない（新しい正本を作らないため）。見比べて直すのは人かエージェントで、tadori は「古い」と知らせるだけ
- デスクトップアプリでは、正本のリンクを窓の中ではなく OS の既定のブラウザで開く（窓が外のページへ移ると戻れないため）。開くのは http と https だけ。Tauri 公式の opener プラグインを使う（MIT/Apache-2.0、フォルダ選びの dialog と同じ出どころ）

## 2026-11-09 画面のテストは Playwright で、架空の見本を開いて確かめる

画面は素の JavaScript で、これまでテストが無かった。スクロールの範囲・リンクの飛び先・エージェントの札のはみ出しのように、画面で開かないと分からない崩れが続いた。

- Playwright（Apache-2.0・Microsoft が保守）で、`tadori serve` が開いた架空の見本を、実際のブラウザで確かめる（`pnpm e2e`）
- 見るのは見た目の細部ではなく、人が使うときに困ること（上の帯が動く・押せないリンク・はみ出す札・担当で絞れない）
- 手元の Windows では入っている Edge を使い、ブラウザを別に落とさない。CI（`.github/workflows/ci.yml`）では Chromium を入れる
- CI は push と pull request のたびに、型・単体のテスト・画面のテストを回す。デスクトップアプリ（Rust）はインストーラーを作る側で建てる
- 画面の TypeScript 化は、テストで振る舞いを押さえてから行う（先に変えると、壊したかどうかが分からない）

## 2026-11-09 画面は JavaScript のまま、TypeScript で型を検査する（段階を分けて進める）

画面（packages/ui/static）は、tadori serve がそのまま配る素の JavaScript で、ビルドの段が無い。TypeScript で書き直してビルドを足すと、CLI とデスクトップアプリの配り方まで変わる。

- まず `checkJs` で、いまの JavaScript を TypeScript の検査にかける（`pnpm --filter @tadori/ui typecheck`。commit 前の検査と CI でも回る）
- 画面が受け取るデータの型は、サーバー（packages/cli）の型をそのまま読む（`static/types.d.ts`）。画面とサーバーで形が食い違えば、検査で止まる
- 第 1 段は「引数に型が書いていない」だけを見逃し、null の扱い・無い項目の読み取り・誤りの型（unknown）を直した。第 2 段で、ファイルごとに JSDoc で引数の型を書き、`noImplicitAny` を有効にする
- 振る舞いは画面のテスト（Playwright）で押さえてから変える

## 2026-11-09 新しい版の確認は「知らせて配布のページを開く」まで。自分で入れ替える更新は署名の鍵ができてから

ヘルプに「バージョンと更新」を置き、起動したときにも 1 日に 1 回、新しい版があるかを確かめる。

- 見に行くのは GitHub の公開リリースの最新の版だけ（`tadori serve` が代わりに見る）。案件の中身や手元の情報は送らない。`TADORI_UPDATE_CHECK=off` で切れる
- 新しい版があれば、上の帯に札を出し、配布のページを OS のブラウザで開けるようにする。確かめられないときは、その理由を出し、「最新」と決めつけない
- アプリが自分で落として入れ替える更新（Tauri の updater）は、配る物に署名する鍵が要る。鍵は人が作って GitHub の秘密に置くもので、AI は作らない。鍵ができたら、release.yml で更新の情報（latest.json）と署名を出し、updater を足す

## 2026-11-09 英語を基本にし、日本語も出す（画面・文・CLI・MCP・使い方・紹介ページ・README）

日本の外でも使えるようにする。仕様から試験・指摘までを ID でつなぐ考え方は、規制のある分野（医療機器・車載・航空など）では国を問わず要る。

- 英語の文をそのまま鍵にして、日本語は辞書で引く（画面は packages/ui/static/i18n-ja.js、core と CLI は src/i18n-ja.ts）。辞書に無い文は英語で出る
- 言語は、人が選んだもの（画面はこの PC に覚える）→ TADORI_LANG → OS／ブラウザの言語 → 英語。画面は頼みごとに言語を添え（x-tadori-lang）、サーバーはその頼みの間だけその言語で返す
- 案件の中で人が書いた言葉（工程・列・1 日の進行の文の設定など）は訳さない。台帳に書くデータ（承認の状態・チェックの記録の結果など、あとで読み戻すもの）も訳さない
- いまある日本語の案件の見た目は変えない（日本語の OS では日本語のまま。テストは日本語に固定して、これまでの文が 1 文字も変わらないことを確かめている）
- 紹介ページは英語を / に、日本語を /ja/ に置き、hreflang で対応を示す

## 2026-11-09 値で判定するルール（allowed と、only の「a|b」「!=」）

「試験の結果は OK か NG のどちらか」「本番以外の環境の記録だけ見る」のような、列の値で決まる約束を、ルールに書けるようにする。

- 判定の種類 `allowed` を足す。from の種類の行の field 列が、`values` 列に `|` で区切って書いた値のどれかであること。空の行はここでは見ず、`filled` に任せる（1 つの漏れを 2 つのルールが別の言い方で出さないため）
- `only` は `列名=値` に加えて、`列名=a|b`（どれか）と `列名!=値`（それ以外）を書ける。「NG の記録には不具合票がある」は、`covered RUN → BUG` に `only` を `result=NG` と付けて書く
- 式や計算は入れない。TSV を開いた人がそのまま読める書き方に留め、点数や割合も出さない
- 前に書いた rulesets のファイルはそのまま読める（`values` 列は無くてよい。画面や MCP から足すと、列は後ろに足される）

## 2026-11-09 前の作業日の「次の作業日」を、次の日の「今日」へ持ち越す

1 日の進行で、人が前の作業日の「次の作業日」に書いた予定を、次の作業日の朝に書き直さなくて済むようにする。

- 前の作業日は、その日より前で 1 日の進行のファイルがいちばん新しい日（休みの日を飛ばすため、暦の前日にしない）
- 持ち越すのは人が足した行・直した行だけ。WBS から自動で出た行は、その日の WBS から作り直されるので持ち越さない（2 回出さない）
- 前の日のファイルは書き換えない。持ち越した行は新しい日では自動の行と同じ扱いで、直す・消すとそれが残る
